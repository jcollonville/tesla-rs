# tesla-fleet-telemetry

Decode Tesla Fleet Telemetry and accept it on a mutual-TLS websocket.

The protobuf files and the client CA bundles are copied from [teslamotors/fleet-telemetry](https://github.com/teslamotors/fleet-telemetry) commit `bb7c8a931e46da3b3eb6d20a67541c8f755f1ee6` and stay under Apache-2.0. See `NOTICE`. This crate is not affiliated with Tesla.

```rust
use tesla_fleet_telemetry::{DeliveryPolicy, FleetTelemetryConfig};

let config = FleetTelemetryConfig::builder("telemetry.example.com", 443, "ca-pem")
    .field("Soc", 60)
    .field("Location", 10)
    .delivery_policy(DeliveryPolicy::Latest)
    .build()
    .expect("config");
let body = config.request_body(["VIN"]).expect("json");
let _ = body;
```

`body` is the JSON for `POST /api/1/vehicles/fleet_telemetry_config`. `tesla-fleet-api`'s `TelemetryConfig` deserializes the same object, including `delivery_policy`, `minimum_delta`, `resend_interval_seconds`, and `include_fields`.

## What it decodes

* `vehicle_data.proto` `Payload` / `Datum`: every `Field` number and every `Value` oneof arm. Unknown field numbers and unknown enum discriminants are kept.
* `vehicle_alerts`, `vehicle_errors`, and `vehicle_connectivity`.
* The FlatBuffers websocket envelope. The upstream repository does not publish the `.fbs` file. `envelope` reconstructs it from the generated Go in `messages/tesla/` (flatbuffers 23.3.3). Acks are not an empty `FlatbuffersStreamAck` table: the reference encoder writes `message_type = 5` and points `message` at an empty string. Tests compare encoded bytes with fixtures produced by that Go code.

`decode_vehicle_data` applies the reference server's body fixes: location strings, scientific-notation strings, legacy automatic-emergency-braking values from client version `1.3.0`, and alert timestamps stored as unix milliseconds. The prost message after those fixes is available from `raw()`. The original protobuf bytes are kept on `IncomingRecord::payload`.

## Receiver

The `server` feature is on by default. `TelemetryServer` listens with `tokio-tungstenite` and `rustls`, requires a client certificate, and checks it against the vendored Tesla prod or eng bundle (or a PEM you supply). The certificate's subject common name is the device id, with `.` replaced by `-`. Issuer common name and extended-key-usage OIDs select the device type, following `messages/identity.go`.

Parsed records are acked the way the reference server acks when reliable acks are off. A frame larger than 1 MiB, or a frame that is not a FlatBuffers envelope, gets the error payload `incorrect message format`. Unknown message types are acked once. Incoming acks are ignored. Connect and disconnect are yielded as `connectivity` records. There is no storage and no rate limit.

```bash
export TESLA_TELEMETRY_CERT=server.crt
export TESLA_TELEMETRY_KEY=server.key
cargo run -p telemetry-receiver
```

## Verification limits

Tests use binaries generated by the Go reference (`tools/gen_fixtures.go`) and a local mutual-TLS handshake with an `rcgen` CA whose issuer common name is `TeslaMotors`. They do not open a network connection and they do not use a real vehicle certificate.

`rustls` / webpki validates the client chain. Go's `crypto/x509` is more permissive, so a production Tesla chain can fail here even though the reference server accepts it. The vendored bundles parse as trust anchors; that does not prove a vehicle certificate chains to them.
